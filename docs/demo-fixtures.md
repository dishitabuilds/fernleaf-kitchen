# Rolling reviewer data

Run `pnpm db:migrate` followed by `pnpm db:seed`. The seed inserts missing staff and initial configuration, adds a separate realistic review catalogue, then appends dated operational scenarios. It never resets the database. The four staff identities remain `admin@test.com`, `kitchen@test.com`, `dispatch@test.com`, `driver@test.com`, each initially using `Test@1234`; passwords are hashed. Existing staff edits are preserved.

The additive review configuration supplies three companies and 24 employees, 12 dishes, five reusable options, required grain/optional accompaniment groups, three stations, ordinary/secret categories and explicit/derived tiers. Combined with the initial configuration this provides four companies, 26 employees and 15 dishes. Review Day Meals and Cedar Health Centre accept all seven days; Northstar Design Studio demonstrates weekdays. The original missing-price example is retained.

Each scenario has deterministic namespaced UUIDs keyed by date, company and scenario. Each operational stop groups two employee orders by the actual address and exact time. Current-day scenarios include pending Kitchen work, Kitchen-ready Dispatch work and a Driver-owned Out-for-delivery stop. Cancelled/rejected purchases have no active work. Recent dates supply Delivered history and fixture-only paid/unpaid invoices plus labelled internal credits. Future dates supply Draft/Placed orders with future kitchen cutoffs. Quotes, option validation, prices, sums, purchase snapshots and delivery grouping use the authoritative backend rules.

Historical actual times are explicitly labelled **Generated demo history** in order/drop timelines. They model coherent prior operations and remain separate from ordinary HTTP ordering; reviewers cannot bypass cutoffs through a fixture endpoint. The driver query uses the real Asia/Kolkata date. Today is never frozen to the submission date.

Set `DEMO_FIXTURES_ENABLED=true` on the synthetic assignment API. The Nest process runs startup catch-up and checks the Asia/Kolkata date each minute, appending at the first minute after local midnight. Existing cutoff scheduling still performs startup/minute catch-up through its shared idempotent service. Database advisory transaction locks serialize concurrent fixture workers during deployments. Creation is insert-if-missing; completed/edited orders, notes, pricing, employee transfers, company calendars and billing are preserved. Retired configuration or an already-owned drop causes a scenario to be skipped, with counts logged. The seed no longer invoices arbitrary existing reviewer orders.

An awake API supports midnight work. A sleeping host performs catch-up on its next startup; its reviewer-day fixture refresh is therefore delayed until startup succeeds. Observe `demo_fixtures_appended` / `demo_seed_completed` structured log events, database health and cutoff logs. Failed fixture attempts log a safe error and retry on the next minute. Keep database/hosting available and check health/logins for at least 14 days after actual submission. Hosting availability is a separate deployment gate.

## External catch-up for sleeping hosts

Configure a private random `MAINTENANCE_TOKEN` containing at least 32 characters (maximum 512, no whitespace). Unset/empty disables the external endpoint. API startup validates the setting. Keep it in the hosting environment and scheduler's secret store, never the repository, README, client bundle or browser settings.

An external scheduler may send `POST /api/v1/jobs/maintain` with `Authorization: Bearer <private token>` and `Origin: <exact WEB_ORIGIN>`. No browser session is used. The shared access guard still requires that exact Origin. An unset token returns `404 JOB_DISABLED`; absent/wrong bearer credentials return `401 JOB_UNAUTHORIZED`; a wrong Origin returns 403. Token hashes are compared in constant time. A successful response reports cutoff date/confirmation/cancellation/skipped/failure counts and, when `DEMO_FIXTURES_ENABLED=true`, appended fixture counts. It exposes no purchase records or credentials. Failures return sanitized `503 MAINTENANCE_FAILED` and a safe server log for retry.

The endpoint invokes the same idempotent cutoff service as startup/manual actions and the same append-only fixture builder. For a sleeping API, schedule independent calls and allow for cold-start latency/retries; the host's in-process minute timer cannot run while asleep. The provider/scheduler setup and cold-start measurements must be verified separately on the live deployment. The endpoint is implemented for that fallback, not evidence that an external schedule is already configured.

For the synthetic Render assignment service, `pnpm --filter @fernleaf/api start:demo-deploy` applies committed migrations, runs the idempotent demo seed, then starts production output. The ordinary `start:deploy` retains migration-plus-start behavior. `pnpm --filter @fernleaf/api seed:demo` runs the seed CLI directly. Use the demo startup only for this synthetic deployment.

Focused external-job verification command: `pnpm --filter @fernleaf/api test:integration --testPathPatterns=jobs`. On 4 October 2026, **6/6 cases passed in 15.873 seconds** on isolated PostgreSQL, covering token/Origin rejection without mutations, optional disablement, passed-cutoff repetition, fixture preservation, token configuration and sanitized failures. API typecheck and focused ESLint also passed. External scheduler configuration and live cold-start execution remain deployment checks.
